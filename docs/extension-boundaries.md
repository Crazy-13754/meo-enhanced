# 主编辑器与独立扩展的职责边界

新增、修改或审查独立扩展、扩展接入接口，以及由扩展需求触发的编辑器改动时，按本规则判断归属。按能力的职责和复用范围拆分，不按需求名称或最初提出需求的功能归属整项改动。

## 归属原则

| 归属 | 负责内容 | 示例 |
| --- | --- | --- |
| 主编辑器 | 文档与编辑状态的权威管理、编辑器公共交互、共享呈现规则及接入接口 | 文档修订与编辑事务、工具栏入口样式、主题、分栏与全屏、焦点、正文定位与位置标记、扩展注册与释放 |
| 独立扩展 | 功能身份、特有语义与算法、功能内部交互及专属依赖 | 扩展名称和图标、Markmap 解析与渲染、导图节点选择和折叠、导图画布拖动与缩放、特有语法兼容 |
| 双方接口 | 扩展表达意图或提供数据，主体执行属于自己的行为 | 扩展提供入口名称与图标，主体绘制按钮；扩展提供节点对应的源码位置，主体按当前模式定位正文 |

新增非通用 Markdown 能力优先作为可选独立扩展实现；它需要的编辑器共用能力可以留在主体。已有内置功能保持现有归属，不为统一形式主动拆出。共用规则覆盖其适用的内置功能与扩展入口，不能只为某个扩展复制一套。

新增扩展优先复用既有能力。修改公共交互，应说明对原有使用场景的收益；安装扩展本身不应迫使已有功能增加标题栏、改变布局或重复入口。共用按钮规则与接口，不意味着不同内容必须采用同一种工具栏结构。

## 判断与实施

1. **先确认状态所有者和已有能力。** 涉及文档修改、选择、焦点、视口或布局时，复用当前所有者的操作；扩展通过接口请求，不直接操纵主体的内部 DOM、私有状态或持久化流程。未来需要编辑文档的扩展也应经过主体的编辑事务与历史管理。
2. **把共用机制与功能内容分开。** 去掉扩展名称后仍成立的编辑器规则，归主体统一实现；依赖特有语法、节点模型、算法或第三方渲染库的部分，归扩展。主体接口使用通用概念，避免按扩展 ID 分支、硬编码扩展图标或识别其专属语法。
3. **接口按当前需求提供。** 优先使用已有接口；缺少能力时，补充能满足实际用例的最小契约，并明确输入、状态归属、失败和释放行为。第一个扩展也可以推动合理的公共接口，无需等待第二个；仅因未来“可能通用”而设计的平台、配置层或回调暂缓实现。
4. **实现只维护一处。** 主体维护公共规则，扩展消费接口和主题变量，并将自己的样式限制在所属内容区域。扩展专属运行依赖随扩展打包；未安装或未启用扩展时，主体仍可独立使用，不加载其专属运行资源。

界面规则的具体内容维护在[界面设计约定](ui-design-guidelines.md)，本文件只规定职责归属。接口升级同时更新双方契约及接入说明，明确实际需要的兼容行为，避免在两边各加一层猜测式兼容。

## 验证与交付

- 实施前简要明确主体改动、扩展改动和接口改动；普通归属判断自主处理，显著扩大范围的重构先说明取舍。
- 按[测试工作流](testing-workflow.md)验证受影响部分。修改公共规则时覆盖相关内置使用方；修改接口时覆盖双方联动、缺失可选能力和释放后的行为，异步操作还应检查过期结果。仅修改扩展内部实现时，验证该扩展及其实际受影响的接入行为。
- 交付时分别说明主体和扩展改了什么、验证了什么。发现越界实现时，在当前任务范围内修正，不顺带迁移无关功能。
